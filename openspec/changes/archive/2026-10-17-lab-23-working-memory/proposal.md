# Proposal

## Why

Message history (L21, L22) remembers what was said. Working memory remembers what matters about the user, such as their name, home airport, seat and dietary needs, as a structured record that the agent reads on every turn and updates as it learns. Learners need to see:

- how a schema-based working memory is configured,
- how it is updated and retrieved, and that it follows the user into a new conversation,
- where validation happens and where it does not.

The installed Mastra validates updates the agent makes through its tool, but stores direct API writes without validation. That gap is the lesson.

## What Changes

- **New lab `lab-23`** (Module 05).
- **Working memory setup.** `Memory` is configured with `workingMemory: { enabled: true, scope: 'resource', schema: PreferencesSchema }`, where `PreferencesSchema` is a strict Zod object: name, home airport (IATA), seat, dietary list and currency.
- **Path 1, conversational updates.** The agent's `updateWorkingMemory` tool (generated by Mastra from the schema) saves preferences from the learner's messages. An invalid request, such as a seat on "the roof", is rejected by the tool's input validation, and the stored memory is unchanged.
- **Path 2, direct updates** (a settings page). `ProfileService.update(user, patch)`:
  1. validates the patch with the strict partial schema;
  2. merges it with the current profile;
  3. re-validates the whole profile;
  4. writes it with `memory.updateWorkingMemory`.

  Bad updates are rejected with field-level reasons. A toggle disables validation to show that raw writes are accepted and replace the profile.
- **Next conversation.** A follow-up in a **new thread** for the same user is answered from working memory.
- **Retrieval.** The stored profile is read back with `getWorkingMemory` and must pass the strict schema.
